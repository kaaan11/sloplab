# Benchmark Methodology

This document defines every metric SlopLab computes and the protocol used to produce
benchmark numbers. Metric implementations live in `src/sloplab/scoring/metrics.py`;
this document is the normative definition they implement.

## Scope of claims

Benchmark results answer exactly one question: *how robust is a given evaluator's
triage behavior on this corpus, under these mutations?* They do not measure general
security-review quality and must not be quoted as such.

## Case population

A benchmark run evaluates two kinds of cases:

1. **Canonical cases** - the committed fixture reports with their manifest ground
   truth. Expected decisions derive from report class: valid -> `accept`,
   invalid -> `reject`, review -> `needs_manual_review`.
2. **Derived (mutated) cases** - generated by the mutation planner from canonicals.
   Each carries an explicit `expected_decision` in its provenance manifest.

Derived cases split into:

- **Degrading mutations**: expected decision differs from the parent class default
  (the mutation should change what a correct triage system does).
- **Quality-neutral mutations**: expected decision equals the parent class default;
  correct triage should be unchanged (professionalization, noise).

No-op exclusion (v0.2.2, R01): an operator plan whose application leaves the
report text byte-identical to its parent is **never written** as a derived case
(the materializer skips plans whose output equals the parent text or whose
operator reports a machine-readable no-op signal). Every written adversarial case
therefore differs from its parent; case counts quoted for v0.2.2 onward reflect
this exclusion.

## Metric definitions

### Decision accuracy

`correct / total` over all scored cases, where correct means the evaluator's
decision equals the case's expected decision. Reported overall and per report class.

### False reassurance rate (primary risk metric)

Among cases whose expected decision is NOT `accept`: the fraction where the
evaluator returned `accept`. High false reassurance means broken or incomplete
content passes automated triage.

### Over-rejection rate

Among accept-expected (valid) cases: the fraction rejected. High values mean the
evaluator suppresses genuine reports.

### Mutation detection rate

Among degrading mutations: the fraction where the evaluator matched the expected
(mutated) decision rather than the parent's expectation.

### Robustness delta (decision drift)

For quality-neutral mutations: how often the evaluator's decision differs from the
decision it gave the canonical parent. Low is good; substance-neutral edits should
not wobble automated triage.

### Presentation susceptibility

Acceptance-rate delta between presentation-mutated cases (`professionalize_language`,
`confidence_overstatement`) and their canonical parents, computed over non-accept-
expected cases only. Positive values mean polished-but-broken content buys acceptance.

### Dimension error

Mean absolute error per quality dimension over cases that carry
`expected_dimensions` (all V1 corpus fixtures do). Dimensions: reproducibility,
evidence_completeness, claim_evidence_consistency, impact_calibration,
scope_consistency.

### Calibration error

Expected calibration error (ECE) over 10 equal-width confidence bins using binary
correctness as the outcome.

### Robustness Score (auxiliary)

A weighted summary for convenience ranking only:

```
40% mutation detection + 25% (1 - false reassurance) + 15% decision accuracy
+ 10% (1 - calibration error) + 10% (1 - presentation susceptibility)
```

Missing components are reweighted by their available mass. Primary results are
always the per-metric values above; never cite the auxiliary score alone.

## Protocol

1. Materialize the suite from a committed YAML config with a fixed `base_seed`.
2. Run each evaluator over the full case set. Evaluators receive labels only via
   `EvaluationContext.labels` (consumed by the oracle; ignored by content-based
   evaluators, enforced by tests). Identity hygiene (v0.2.2, R04): evaluators
   additionally receive only an opaque, deterministic case handle - never a
   case id, fixture id, or report path that encodes mutation identity; the true
   identifiers are restored in recorded provenance.
3. Record one JSONL line per case evaluation plus a run-metadata header (version,
   git commit when available, suite hash, seed, timestamp).
4. Group derived cases under their parents; never count variants as independent
   real-world reports.
5. For stochastic evaluators (e.g., LLM adapters), run at least three repetitions
   and report mean and spread; deterministic evaluators are byte-reproducible by
   construction.
6. Inspect surprising results manually and document them; never adjust labels to
   improve any evaluator's numbers.

## Known v0.1.0 baseline behaviors

The rules baseline is deliberately imperfect (it is a floor to beat, not a ceiling):

- It misses roughly a quarter of degrading mutations in the v1-core suite, mostly
  evidence removals phrased unusually.
- A small residual false reassurance rate remains on polished presentation-pair
  members, which is precisely the phenomenon the benchmark is designed to expose.
- Its uncertainty detector overlaps stylistically with this corpus's review-class
  phrasing; see the note in `evaluators/rules/baseline.py`.
